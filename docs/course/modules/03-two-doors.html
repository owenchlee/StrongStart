03

Two Doors

Links for the public, Google sign-in for staff: how StrongStart stays safe without anyone typing a password.

Two kinds of visitor

Parents and facilitators never create an account or remember a password. Staff never type one either. How is that safe?

Picture the site as a museum with two doors. Visitors get a wristband: a token hidden inside a link that admits them to exactly one exhibit. Staff wear a badge: a session cookie earned by signing in with Google, and it opens every back-office door.

🎟️

Parents, facilitators and partners. The URL itself is the key, and each key opens one exhibit only.

Nothing is open by default. A door with neither a wristband slot nor a badge reader is simply locked.

Module 2 showed the order of the middleware in server.js: auth before the gate, the gate before static files. This module is about what that gate does.

The gate on every request

requireStaff is the badge reader. It is one function that the server runs on every single request, before any route gets a say.

Snippet A · src/auth.js · lines 99–108
CODE 

export async function requireStaff(req, res, next) {
  const method = req.method === 'HEAD' ? 'GET' : req.method;
  if (!authRequired) { req.staff = LOCAL_STAFF; return next(); }
  if (!isDashboardPage(req.path) && !isApi(req.path)) return next();
  if (isApi(req.path) && PUBLIC_API.some(([m, re]) => m === method && re.test(req.path))) return next();
  const staff = await currentStaff(req);
  if (staff) { req.staff = staff; return next(); }
  if (isApi(req.path)) return res.status(401).json({ error: 'Staff login required' });
  res.redirect('/login.html');
}
PLAIN ENGLISH

Here is the gate. Express hands it req, res and next: the request, the reply, and a way to say pass. It is async because it may have to wait for the database.

Treat a HEAD request as a GET. In HTTP they ask the same question, HEAD just wants the headers.

If staff login is switched off, pretend everyone is a local staff member and wave them through. (The hackathon setting; see the caveat below.)

Not a dashboard page and not under /api? Then it is a public page or a static file: no badge needed, pass.

Under /api but on the allow-list, with the right method and a matching pattern? That is a wristband door: pass.

Otherwise read the cookie, hash it and look for a live session in the database.

Found one? Pin the staff record to the request so the route knows who is asking, then pass.

No session and this is an API call: answer 401 with a short JSON error the dashboard can display.

No session and this is a page: redirect the browser to the login page.

End of the gate. Every request leaves through exactly one of these exits.

Read top to bottom, the gate is a short queue of questions. The first yes wins.

1
Is login switched off?

Everyone is treated as local staff. Demo only.

2
Is this a public page or a static file?

Not the dashboard, not under /api. No credentials needed.

3
Is this /api address on the allow-list for this method?

A wristband door. The token in the path does the checking later, inside the route.

4
Does the cookie match a live session?

A valid badge. The staff record rides along as req.staff.

✕
None of the above: locked.

API calls get 401 Staff login required; pages are sent to /login.html.

The allow-list

PUBLIC_API is the list of wristband doors. Every entry is a pair: an HTTP method and a regex the path must match.

Snippet B · src/auth.js · lines 74–80 (the list continues to line 95; 20 entries in total)
CODE 

// Default-deny: everything under /api and the dashboard page requires staff, except this allow-list
// of public routes (see WORKLOAD.md "Who can access what"). New API routes are protected automatically.
const PUBLIC_API = [
  ['POST', /^\/api\/inbound-email\/?$/],              // email provider webhook (add a shared secret separately)
  ['GET', /^\/api\/order-form\/[^/]+\/?$/], ['POST', /^\/api\/order-form\/[^/]+\/?$/],
  ['POST', /^\/api\/feedback\/[^/]+\/?$/],            // parent feedback form
  ['POST', /^\/api\/feedback\/[^/]+\/photos\/?$/],    // facilitator photo upload
PLAIN ENGLISH

A note to future developers: the rule is default-deny. Everything under /api and the dashboard page needs a badge...

...except the routes listed here, the wristband doors. New API routes are protected automatically; there is nothing to remember.

The allow-list begins. Each entry pairs a method with a pattern for the path.

The email provider POSTs each incoming email here, a webhook. The comment is a to-do: this door still needs a shared secret.

The order form for one kit request: GET to read it, POST to submit it. The [^/]+ part is where the token sits.

Parents POST their feedback here, token in the path.

Facilitators POST photos of paper forms here. The list runs on to line 95: twenty doors in all.

💡
Key Insight: default-deny with an allow-list

Default-deny with an allow-list is the safest shape for permissions: forgetting to add a route makes it too locked, which someone notices immediately, instead of too open, which nobody notices.

🪪
Adding a staff route?

Write the route. Touch nothing in auth.js. It is locked from the moment it exists.

🎟️
Adding a public route?

Write the route, then add one line to PUBLIC_API: its method and a regex with a slot for the token.

Why a random token and not /feedback/12

Program number 12 is easy to guess, and so is 13. A wristband like /feedback/8f3aQx… is not. Public URLs use the random token, never the numeric id, so knowing one link tells you nothing about any other.

Snippet C · src/routes/feedback.js · lines 29–33
CODE 

const TOKEN_RE = /^[A-Za-z0-9_-]{16,64}$/;
async function programByToken(token) {
  if (!TOKEN_RE.test(token || '')) return undefined;
  return one('SELECT id, name, location, token FROM programs WHERE token=$1', [token]);
}
PLAIN ENGLISH

What a valid wristband looks like: 16 to 64 characters, only letters, digits, underscore or hyphen.

Given a token from the URL, find the program it belongs to.

If the token is missing or does not look like a wristband, give up at once and return undefined. The database is never even asked.

Ask the database, in SQL, for the one program whose token matches. $1 is a placeholder, so the token can never be mistaken for part of the query.

Done. The caller gets one program, or nothing.

A guessable id would let anyone submit fake feedback for any program, or read any order form. The random token is the whole permission: engineers call this a capability link.

The badge works on the same idea in reverse. The cookie is a random secret too, and the database only ever stores its fingerprint.

Snippet D · src/db.js · lines 115–119
CODE 

-- Server-side sessions; id is the SHA-256 of the cookie value, so a leaked DB can't be replayed.
CREATE TABLE IF NOT EXISTS sessions (
  id TEXT PRIMARY KEY, staff_id INTEGER NOT NULL REFERENCES staff(id) ON DELETE CASCADE,
  expires_at BIGINT NOT NULL, created_at TIMESTAMPTZ DEFAULT now()
);
PLAIN ENGLISH

The badge register. The id column holds a SHA-256 fingerprint of the cookie, not the cookie itself, so a leaked database cannot be replayed.

Make the sessions table if it is not there yet; safe to run on every start.

One row per badge: its fingerprint as the primary key, and the staff member it belongs to. ON DELETE CASCADE means deactivate the staff row and their badges vanish with it.

When the badge expires (a BIGINT moment in time) and when it was issued.

End of the table.

Four small things make the two doors hold.

#

Hashed session ids

The database keeps the fingerprint, the browser keeps the key. Stealing the register gets you nothing.

🔐

PKCE on Google sign-in

The OAuth flow uses PKCE, so intercepting the middle of a sign-in does not let anyone finish it.

✓

Active staff row required

A verified Google email is not enough. It must match an active row in the staff table.

⏏

Deactivate deletes sessions

Switch a staff member off and their badges stop working on the next request, not in 7 days.
