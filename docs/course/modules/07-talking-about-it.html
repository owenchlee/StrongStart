Four defensive habits you can name

Engineers will ask how the site protects itself when strangers can post forms with no login. These four habits are the answer, and each one lives in a place you can point to.

🧼

Input cleaning + length caps

Helpers in util.js trim every field and cut it at a maximum length, so a ten-megabyte name cannot fill the database.

⏱️

Rate limits per IP and token

A rate limit counts requests per IP address and per link token, and answers slow down to a 429 after the cap.

🔒

Atomic claims in SQL

State changes use one SQL statement like UPDATE … WHERE status='shipped' RETURNING, so two clicks at once cannot both succeed. That is what atomic means.

🧯

HTML escaping everywhere

Anything a user typed passes through escapeHtml before it is shown, so a form answer containing code is displayed as text, never run. This is HTML escaping.

Here is habit two in full. One small function makes a reusable middleware that any route can put in front of itself.

CODE 

export function rateLimit(a, b, c) {
  const { name = 'rl', max = 30, windowMs = 10 * 60 * 1000 } =
    a && typeof a === 'object' ? a : { name: a, max: b, windowMs: c ?? 60_000 };
  return (req, res, next) => {
    const key = `${name}|${req.ip}|${req.params?.token || ''}`;
    const now = Date.now();
    let h = hits.get(key);
    if (!h || h.reset < now) { h = { n: 0, reset: now + windowMs }; hits.set(key, h); }
    if (++h.n > max) {
      res.set('Retry-After', String(Math.ceil((h.reset - now) / 1000)));
      return res.status(429).json({ error: 'Too many requests. Please wait a few minutes and try again.' });
    }
    next();
  };
PLAIN ENGLISH

Define a function called rateLimit that other files can import. It accepts up to three inputs.

Set the defaults: a label of rl, a cap of 30 requests, and a window of ten minutes written as milliseconds.

If the caller passed a settings object, use it; if they passed three plain values, rebuild them into the same shape with a one-minute fallback window.

Hand back a middleware: a function that will run for each incoming request before the real work.

Build a key that combines the label, the caller's IP address and the link token in the address, so each person and each link is counted separately.

Note the current time.

Look up this key in the in-memory tally called hits.

If there is no tally yet, or the old window has expired, start a fresh one: zero hits, resetting one window from now.

Add one to the count. If that pushes it over the cap...

...tell the caller how many seconds to wait using the standard Retry-After header...

...and stop here with status 429 and a friendly JSON message.

End of the over-the-cap branch.

Otherwise, let the request through to the real handler.

End of the middleware the function hands back.

One more guard worth naming out loud. The inbound email webhook checks a shared secret using a constant-time comparison so an attacker cannot measure how many characters matched.

src/routes/orders.js · lines 90–98
CODE 

function inboundAllowed(req) {
  const secret = process.env.INBOUND_EMAIL_SECRET;
  if (!secret) {
    if (!warnedNoSecret) { warnedNoSecret = true; console.warn('[inbound-email] INBOUND_EMAIL_SECRET is not set: the webhook accepts anyone. Set it in production.'); }
    return true;
  }
  const given = req.get('x-inbound-secret') ?? (typeof req.query.secret === 'string' ? req.query.secret : '');
  return timingSafeEqual(sha(given), sha(secret));
}
PLAIN ENGLISH

A yes-or-no function: is this inbound email request allowed in?

Read the expected secret from the environment variable INBOUND_EMAIL_SECRET.

If no secret has been set at all...

...print a warning once, and only once, that the webhook is wide open and should be locked before production...

...then let the request through anyway, so the demo still works.

End of the no-secret branch.

Otherwise, take the secret the caller offered: first from the x-inbound-secret header, or failing that from a secret value in the query string, or an empty string if neither is present.

Compare a hash of each side in constant time, so a wrong guess takes exactly as long as a right one.

End of the function.

What is on and what is off

Every outside service, and every safety switch, is controlled by an environment variable. Leave one blank and the feature turns itself off gracefully instead of crashing; set it and the feature wakes up.

TIGER_DATABASE_URL Points the server at hosted Tiger Data. Blank means PGlite runs inside the process, in memory unless PGLITE_DIR is set.
GEMINI_API_KEY Turns on all AI: handwriting reading, translation, summaries and tidying dictated text. Blank means the dashboard shows AI as off and those steps are skipped. An API key is the password for a service.
ELEVENLABS_API_KEY Turns on audio: spoken parent answers become text, and text can be read aloud.
CLOUDINARY_URL Turns on cloud image storage for uploaded photos and generated QR sheets.
GOOGLE_CLIENT_ID / SECRET Enables staff sign-in with Google through OAuth, and lets the server create Calendar events and Meet links for training.
REQUIRE_AUTH Set to 1 and the dashboard demands a staff login on every protected route. Off by default so the demo opens straight away.
INBOUND_EMAIL_SECRET Locks the inbound email webhook. Until it is set, anyone who finds the address can post a fake kit request.
ENABLE_JOBS Turns on scheduled background work such as reminders and follow-ups that run on a timer rather than on a click.
SMTP_HOST Points the mailer at a real mail server over SMTP. Blank means every email is still written to the outbox table, just not delivered.

At demo time the server tells you which switches are on the moment it starts. Learn to read these three lines of the console.
