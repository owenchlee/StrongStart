The loop: from one email to a parent’s feedback

What StrongStart does, told as the journey of a single tracking number

What StrongStart does

A facilitator at a library emails babyconnections@… saying “we need 10 kits for our Fall Babies group”. Nobody at Strong Start touches a keyboard, yet within a second the facilitator has a personal order-form link in their inbox.

Here is everything that happened. First, the four business steps the app supports for the Baby Connections program.

📦

1. Kit request

A facilitator emails Strong Start asking for a kit.

🎓

2. Training

The facilitator registers for training, joins a scheduled Google Meet and earns a digital certificate.

👶

3. Run the program

The facilitator runs lessons with children and their parents, using the kit.

💬

4. Parents report back

Parents scan a QR code, speak an answer, or hand in a paper form. Staff see it all on one dashboard.

The app closes the loop: parent-reported outcomes travel all the way back to Strong Start with almost no effort from anyone. The rest of this module follows how.

Follow the tracking number

Think of a parcel tracking number. One random code is minted the moment your parcel is booked, and every later step (packed, shipped, delivered) looks up that same code and moves it to the next status.

StrongStart does exactly this. When the facilitator’s email arrives, the server mints a random token, and every link that follows carries it. Click Next Step to watch one order go round.

Why clicking the link is not enough

Email 3 carries a confirm link. You might expect that clicking it marks the order received, but the server deliberately refuses to do that on a click. It shows a page with a button instead, and only the button press changes the status.

Why? Web browsers talk to servers in two main ways. A GET is what a link click does (just show me the page). A POST is what a form button does (here, do something). Read the comment at the top of this snippet.

⚠️
Why GET must never change anything

Email security scanners at schools and councils open every link in every email before the human sees it. If a GET to /received/TOKEN marked kits received, the scanner would confirm delivery before the box left the warehouse. That is why the state change hides behind a button press.

requireStaff is the badge reader. It is one function that the server runs on every single request, before any route gets a say.

export async function requireStaff(req, res, next) {
  const method = req.method === 'HEAD' ? 'GET' : req.method;
  if (!authRequired) { req.staff = LOCAL_STAFF; return next(); }
  if (!isDashboardPage(req.path) && !isApi(req.path)) return next();
  if (isApi(req.path) && PUBLIC_API.some(([m, re]) => m === method && re.test(req.path))) return next();
  const staff = await currentStaff(req);
  if (staff) { req.staff = staff; return next(); }
  if (isApi(req.path)) return res.status(401).json({ error: 'Staff login required' });
  res.redirect('/login.html');
}
PLAIN ENGLISH

Here is the gate. Express hands it req, res and next: the request, the reply, and a way to say pass. It is async because it may have to wait for the database.

Treat a HEAD request as a GET. In HTTP they ask the same question, HEAD just wants the headers.

If staff login is switched off, pretend everyone is a local staff member and wave them through. (The hackathon setting; see the caveat below.)

Not a dashboard page and not under /api? Then it is a public page or a static file: no badge needed, pass.

Under /api but on the allow-list, with the right method and a matching pattern? That is a wristband door: pass.

Otherwise read the cookie, hash it and look for a live session in the database.

Found one? Pin the staff record to the request so the route knows who is asking, then pass.

No session and this is an API call: answer 401 with a short JSON error the dashboard can display.

No session and this is a page: redirect the browser to the login page.

End of the gate. Every request leaves through exactly one of these exits.

Program number 12 is easy to guess, and so is 13. A wristband like /feedback/8f3aQx… is not. Public URLs use the random token, never the numeric id, so knowing one link tells you nothing about any other.

A guessable id would let anyone submit fake feedback for any program, or read any order form. The random token is the whole permission: engineers call this a capability link.

The badge works on the same idea in reverse. The cookie is a random secret too, and the database only ever stores its fingerprint.

Four defensive habits you can name

Engineers will ask how the site protects itself when strangers can post forms with no login. These four habits are the answer, and each one lives in a place you can point to.

🧼

Input cleaning + length caps

Helpers in util.js trim every field and cut it at a maximum length, so a ten-megabyte name cannot fill the database.

⏱️

Rate limits per IP and token

A rate limit counts requests per IP address and per link token, and answers slow down to a 429 after the cap.

🔒

State changes use one SQL statement like UPDATE … WHERE status='shipped' RETURNING, so two clicks at once cannot both succeed. That is what atomic means.

export function rateLimit(a, b, c) {
  const { name = 'rl', max = 30, windowMs = 10 * 60 * 1000 } =
    a && typeof a === 'object' ? a : { name: a, max: b, windowMs: c ?? 60_000 };
  return (req, res, next) => {
    const key = `${name}|${req.ip}|${req.params?.token || ''}`;
    const now = Date.now();
    let h = hits.get(key);
    if (!h || h.reset < now) { h = { n: 0, reset: now + windowMs }; hits.set(key, h); }
    if (++h.n > max) {
      res.set('Retry-After', String(Math.ceil((h.reset - now) / 1000)));
      return res.status(429).json({ error: 'Too many requests. Please wait a few minutes and try again.' });
    }
    next();
  };
PLAIN ENGLISH

Set the defaults: a label of rl, a cap of 30 requests, and a window of ten minutes written as milliseconds.

If the caller passed a settings object, use it; if they passed three plain values, rebuild them into the same shape with a one-minute fallback window.

Hand back a middleware: a function that will run for each incoming request before the real work.

Build a key that combines the label, the caller's IP address and the link token in the address, so each person and each link is counted separately.

Note the current time.

Look up this key in the in-memory tally called hits.

If there is no tally yet, or the old window has expired, start a fresh one: zero hits, resetting one window from now.

Add one to the count. If that pushes it over the cap...

...tell the caller how many seconds to wait using the standard Retry-After header...

...and stop here with status 429 and a friendly JSON message.

End of the over-the-cap branch.

Otherwise, let the request through to the real handler.

End of the middleware the function hands back.

What is on and what is off

Every outside service, and every safety switch, is controlled by an environment variable. Leave one blank and the feature turns itself off gracefully instead of crashing; set it and the feature wakes up.

TIGER_DATABASE_URL Points the server at hosted Tiger Data. Blank means PGlite runs inside the process, in memory unless PGLITE_DIR is set.
GEMINI_API_KEY Turns on all AI: handwriting reading, translation, summaries and tidying dictated text. Blank means the dashboard shows AI as off and those steps are skipped. An API key is the password for a service.
ELEVENLABS_API_KEY Turns on audio: spoken parent answers become text, and text can be read aloud.
CLOUDINARY_URL Turns on cloud image storage for uploaded photos and generated QR sheets.
GOOGLE_CLIENT_ID / SECRET Enables staff sign-in with Google through OAuth, and lets the server create Calendar events and Meet links for training.
REQUIRE_AUTH Set to 1 and the dashboard demands a staff login on every protected route. Off by default so the demo opens straight away.
INBOUND_EMAIL_SECRET Locks the inbound email webhook. Until it is set, anyone who finds the address can post a fake kit request.
ENABLE_JOBS Turns on scheduled background work such as reminders and follow-ups that run on a timer rather than on a click.
SMTP_HOST Points the mailer at a real mail server over SMTP. Blank means every email is still written to the outbox table, just not delivered.
